# NiceIdeas 选型评估：基于 Sharkey vs 自研

> 日期：2026-10-19 · 作者：nicematrix-system agent
> 状态：**已决策 —— 自研**（Xianglin 2026-10-19 14:23 MDT 确认）。本文保留为决策依据。

## 1. 结论

**建议自研**（独立仓库 niceideas，独立服务），**不基于 Sharkey**。

一句话理由：本周最急的部分和产品差异化部分（记事→图文网页、编辑同步、NiceMatrix ID、好看的分享页、长文卡片）
两条路都得自己写；Sharkey 能省的是"通用社交外壳"，但代价是第二套用户体系、一个 27 万行且上游已落后的分叉要长期维护、
界面与产品设计冲突、AGPL 与我们的工程规范无法落地。按 v1 需要的社交范围，自研全部功能约 4 周，与 Sharkey 路线相当，
之后每一步都更快、更可控。

会让我改为推荐 Sharkey 的条件（任一成立）：
- 产品要加入联邦宇宙（与 Mastodon/Misskey 互关互评）作为核心卖点；
- 接受 Misskey 风格的界面，且"两周内拥有全量社交功能（表情回应、通知、搜索、频道、列表…）"比产品体验更重要。

## 2. Sharkey 现状（已核实）

| 项 | 事实 |
|---|---|
| 是什么 | Misskey 的社区分叉；加了 Mastodon 兼容 API、帖子编辑、注册审批等 |
| 版本节奏 | stable 分支仍为 **2025.4.x**（2025-05 起只有补丁/安全版，最后一次 2026-05-20）；develop 为 2025.5.2-dev。仓库里的上游 Misskey 标签已到 2026.10 → **Sharkey 落后上游约一年半** |
| 维护力量 | 近 6 个月 develop 126 次提交，主要来自 2–3 名维护者 |
| 规模 | 后端约 1,000 个 TS 文件；前后端 TS/Vue 约 **26.8 万行**；数据库迁移 417 个 |
| 依赖 | Node + PostgreSQL（推荐 PGroonga 镜像）+ **Redis**（可选 Meilisearch） |
| 许可 | AGPL-3.0：修改后对外提供服务，须公开修改后的源码 |
| 登录 | 本地账号（密码 / 2FA / 通行密钥）。**无 OIDC/外部身份登录**；`OAuth2ProviderService` 是"作为提供方"给第三方授权，不是接入外部 IdP |
| 帖子 | 默认最长 3000 字（`maxNoteLength` 可调）；每帖最多 16 个附件；可见性 public / home / followers / specified；支持编辑（NoteEdit） |
| 长文 | 有 Pages（标题、摘要、题图、块：text / image / note / section），**无音频块**，**不进时间线** |
| 联邦 | 可设 `federation: none` 完全关闭 |
| 第三方 | 实现 Mastodon API（`/v1/apps`、`/v1/statuses`、`/v2/media`、OAuth）；**OmniFire 已有通用 Mastodon 适配器，支持任意实例** |
| 语言 | 自带 zh-CN / zh-TW / en-US / ja-JP |
| 官方提示 | 删号"可能非常耗资源、耗时，数据多时甚至无法删除"；Drive 文件全部公开 |

## 3. 逐项对照：Sharkey 能给多少

| 需求 | Sharkey 现成度 | 还需要做什么 |
|---|---|---|
| 短想法 + 时间线 + 关注 + 主页 | ✅ 完整 | 去掉不需要的功能、改中文体验 |
| 长图文，流里显示摘要，点开全文 | ⚠️ Pages 有块编辑但不进时间线、无音频 | 加音频块；新增"长文卡片"帖子类型，前后端都改 |
| NiceNote 发布 + 改记事同步更新 | ❌ | 写桥接服务：NiceNote 持 NiceMatrix token → 桥 → 以该用户身份调 Sharkey；Sharkey 需新增"内部代用户签发令牌"接口（改源码） |
| 好看、轻量、适合微信打开的分享页 | ⚠️ 有 OG，但页面是重型 Vue SPA【判断】 | 自写服务端渲染分享页（与自研同工作量） |
| NiceMatrix ID 登录、两区同一账号 | ❌ | 改源码：OIDC 登录、按 sub 建/绑账号、关闭本地注册与密码登录 |
| 删号联动（15 天冷静期） | ❌ | 桥接删号；Sharkey 自身删号慢 |
| 第三方发布（OmniFire） | ✅ 短帖几乎零成本（Mastodon API） | 长文无法经 Mastodon API 发布；需另做 |
| 未来定向分享 | ✅ specified/followers 可见性 | — |
| 未来"仅持链接者可见" | ❌ | 改源码 |
| 产品设计（DESIGN.md、独立品牌） | ❌ Misskey 风格、功能密集 | 大量 Vue 改造或接受原样 |
| 工程规范（≤300 行文件、全语种 i18n、单一职责） | ❌ 无法对 27 万行分叉执行 | 需为该仓库豁免规范 |

**粗算**：Sharkey 覆盖"社交外壳"约 70–80%，覆盖"本周核心"约 0–10%，覆盖"产品差异化"约 20–30%。

## 4. 工期对比（同一个 agent 连续推进；客户端由各自 agent 并行）

| 里程碑 | 基于 Sharkey（混合：Sharkey + 自写桥接/分享页） | 自研 |
|---|---|---|
| 本周：NiceNote 图文分享链接 + 编辑同步 + 账号打通 | 1 周（分享页/桥接为自写；Sharkey 只需部署） | 1 周 |
| 社交平台可用（登录、主页、关注、时间线、短帖） | 第 2 周（OIDC 改造 + 去功能 + 中文） | 第 2 周 |
| 长文进时间线（卡片）、Web 端写长文 | 第 2–3 周（改 Pages + 新帖子类型，跨 Vue/后端） | 第 2–3 周 |
| OmniFire 第三方发布 | 第 3 周（短帖≈现成；长文另做） | 第 3 周（OmniFire 新写适配器，可并行） |
| 品牌化界面、审核、上线加固 | 第 3–4 周+（改 Vue 难度最大）【判断】 | 第 4 周 |
| **v1 全部** | **约 4 周，功能更多但界面像 Misskey** | **约 4 周，功能精简但完全贴合** |
| 之后每月 | 合并上游安全版、维护分叉补丁，持续成本 | 只维护自己的代码 |

关键观察：**两条路的第 1 周完全相同**（都写自己的发布服务和分享页），所以本周不受选型影响；选型只决定第 2 周起的社交层。

## 5. 风险对比

| 风险 | Sharkey | 自研 |
|---|---|---|
| 两套用户体系不一致（删号、合号、改名） | 高：永久存在 | 无 |
| 上游落后 + 维护者少 → 安全补丁靠我们追 | 高（2026-03 有协同安全发布） | 只对自己代码负责 |
| 分叉补丁与上游冲突 | 高：登录、令牌、长文、界面都要改核心 | 无 |
| AGPL 公开源码义务（含我们的改动） | 有 | 无 |
| 资源占用（prod-1 当前可用 ~3.7 GB） | 较高：Node 集群 + Redis 约 1–1.5 GB【判断】 | 低：单服务约 0.3–0.5 GB【判断】 |
| 社交功能深度不足（表情回应、通知、搜索…） | 低 | 中：v1 精简，按需迭代 |
| 自研功能的质量风险（时间线性能、滥用） | 低（成熟） | 中：v1 规模小，用简单可靠的方案即可 |

## 6. 其他开源候选（简评）

- **Misskey（上游）**：更活跃，但没有 Mastodon API、没有帖子编辑，同样无外部 OIDC 登录 → 不如 Sharkey。
- **Mastodon**：原生支持 OIDC 登录、支持编辑；但 Ruby + Sidekiq + Redis 更重，默认 500 字、无长文，界面不可定制度高 → 不合适。
- **WriteFreely / Ghost**：只有长文博客，无短帖社交时间线 → 不合适。
