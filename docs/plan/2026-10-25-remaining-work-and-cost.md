## 2. R2 成本

### 2.1 现状（实测）
- 每张照片存 5 份：w480 / w960 / w1600 WebP，1600 宽兼容 JPEG，大于 1600 宽时再加一份大图 WebP。实测 3840×1725 的照片共 1.6 MB，2900×5367 的手机照片共 2.9 MB，其中大图占 60–70%，兼容 JPEG 占 13–18%。
- **公开的媒体在私有桶和公开桶各存一份**：发布时从私有桶读出再写入公开桶，数据要经过 prod2 中转。所以实际是每张照片 3.2–5.9 MB，比需要的多一倍。
- 媒体缓存头是 `max-age=300`：Cloudflare 边缘只缓存 5 分钟，之后每次回源都要读 R2（B 类操作）。头像已经是 1 年 immutable，实测命中缓存。
- 平铺式缓存（Tiered Cache，免费）是关闭的。
- 目前存量很少（生产 1 个头像，staging 约 300 KB），费用接近 0。优化是为了内容增长以后的成本。

### 2.2 方案
- **R1 每张媒体只存一份**（存储减半）：
  - 发布时改为 R2 服务端复制到公开桶，再删掉私有桶里的那份；撤回或注销冷静期时反过来，复制回私有桶，再从公开桶删除。
  - 顺序是先复制、确认成功后再删除，重复执行结果不变，每日维护负责补做中断的移动。
  - 读取媒体时先查私有桶，再查公开桶。
  - 数据不再经过 prod2 中转；R2 删除操作免费。
  - 存量很少，迁移脚本几秒就能跑完。
- **R2 兼容 JPEG 从 1600 宽降到 1200 宽**：它只用作老浏览器的兜底和分享卡片原图，分享卡片本身就是 1200×630。总体积约少 6–8%。
- **R3 缓存**：
  - 先开 Tiered Cache，边缘未命中时先查上层节点，减少回源读 R2。
  - 媒体缓存头改成 1 年 immutable，删除时调 Cloudflare 按地址清缓存。这需要一个有 niceideas.app 区域 Cache Purge 权限的 token，现在的 token 没有这个权限。没有之前先用 1 小时。
  - 同样的问题也在头像上：账号注销后，头像在边缘缓存里最多还能留 1 年。地址是随机的，外人猜不到，但有清缓存能力后应一并清掉。
- **R4 带版本号的 CSS / JS**（`?v=` 版本号）设为 1 年 immutable，减少回源和重新验证。
- 可选（需你定）：大图上限从 4096² 降到 3072²。每张照片约少 25%，但放大查看的清晰度会下降。我建议保持现状。

## 3. 服务器性能（prod2：2 核、3.8 GB，与 Discourse / NiceSpace / 邮件共用；swap 已用 1.2 GB，可用内存约 1 GB）

NiceIdeas 现在常驻约 515 MB：2 个网站进程各约 160 MB，cluster 主进程 53 MB，worker 141 MB。

- **P1 NOTIFY/LISTEN（即 W1）**：worker 6 小时空闲用了 26 秒 CPU，预计降到约十分之一，空闲查询每分钟约 90 次降到约 3 次。
- **P2 网站进程内存**：
  - 网站进程里的 sharp（图片处理库）关闭缓存、并发设为 1，worker 已经这样设置；
  - 网站和 worker 的服务加 `MALLOC_ARENA_MAX=2`，减少图片处理后内存不释放。
- **P3 生产网站改为 1 个进程**：现在的流量 1 个 Node 进程绰绰有余，进程只有 1 个时也不再起 cluster 主进程，进程崩溃由 systemd 重启。预计省约 210 MB，流量涨了再改回来，只需改环境变量。staging 保持 4 个进程不变。
- 以后再做：网页上传图片现在在网站进程里处理，可以改成交给 worker，网站进程就不会被大图拖慢。改动较大，等上传量上来再说。
